### Почему Mirror

- Встроенный поиск в LAN (`NetworkDiscovery`) и подключение по IP — ровно наши сценарии.

| UE | Mirror |

## 5. Сетевая архитектура

### Режимы

1. **Локальная сеть** — один игрок Host, остальные находят через `NetworkDiscovery` или вводят локальный IP.
2. **Интернет по IP** — headless-сервер (дома с белым IP или на VPS), подключение по IP/домену, порт `7777/UDP`.
3. **Одиночная игра с ботами** — тот же Host без подключений, боты — серверные игроки. Один код на все режимы (в оригинале логика раздвоена: `MenuGameLocal`/`MenuGame`, `HUD_PWLocal`/`HUD_Multiplayer`).
4. *(Позже, по необходимости)* relay-транспорт (Edgegap / EOS / Light Reflective Mirror), чтобы телефон мог хостить через интернет. Меняется только транспорт.

### Что сделано (MVP)

- `PudgeNetworkManager` (наследник `NetworkManager`) создаётся при старте игры вместе с `KcpTransport` и меню `NetMenu`; сцену трогать не нужно. Сетевые объекты собираются в коде (свои `assetId` и обработчики спавна): герой = префаб `Pudge_Player`/`Pudge_Bot` + `NetworkTransformUnreliable` + `NetHero` + `NetworkIdentity`, одинаково на сервере и клиентах.
- `Simulation.IsProxy` — на чистом клиенте геймплей-компоненты не симулируют (движение, хук, падение, яма, золото, боты), а показывают состояние сервера: `Pudge.ApplyRemoteState`, `HookAbility.ApplyRemoteState`, `HeroInventory.ApplyRemoteState`, `Arena.ApplyRemote*`.
- `NetHero`: SyncVar'ы команды, ника, флагов «жив/падает/пойман», золота и предметов (индексы в каталоге `NetPrefabs`), головки хука (позиция, направление, «летит», «занят», время готовности по `NetworkTime`); `[ClientRpc]` анимаций и «+N монет»; `[Command]` ввода, броска и покупки (сервер сам проверяет кулдаун и золото). Возрождение — `ServerTeleport`, без скольжения из ямы.
- `NetMatch`: счёт обеих команд и объявления серий убийств (с числом рампаг подряд).
- `LocalPlayer` — герой с `PlayerInputController` (в сети его получает только свой герой); HUD, камера и магазин переключаются на него, когда он появляется. `OverlayInput` — пока открыто меню сети, клавиши и мышь не уходят в игру.
- Движение пока без предсказания на клиенте: ввод → сервер → `NetworkTransform` (в LAN задержка незаметна, через интернет — RTT).

### Сетевая модель хука (дальше)

1. Клиент сразу рисует предсказанный хук и шлёт `CmdCastHook(dir, clientTick)`.
2. Сервер проверяет кулдаун/состояние и создаёт компактное состояние `HookState {origin, dir, speed, range, startTick, phase, targetId}`. Клиенты считают позицию хука аналитически — трансформ каждый кадр не синхронизируется.
3. Попадание считает сервер с **компенсацией задержки**: история позиций игроков ~500 мс, откат целей на RTT/2 + задержку интерполяции стреляющего (своя реализация, ~150–200 строк).
4. Попадание → `phase = Pull`, цель в состоянии `Hooked`, позицию ведёт сервер вдоль цепи → у Pudge: убийство, золото, серия убийств, таймер респавна, `[ClientRpc]` для звука и FX.
5. Движение (MVP): владелец двигает себя сам, сервер проверяет скорость и границы зоны команды; остальные интерполируются (`NetworkTransform`). Позже при необходимости — серверное движение с предсказанием.
6. Невидимость (Lotar): скрывать объект от противников на уровне видимости сети (interest management), а не только рендером.
7. `sendRate` ~30 Гц.

## 6. Хостинг headless-сервера на домашнем ПК

1. Узнать WAN-IP в роутере (`http://192.168.0.1`) и сравнить с внешним IP (`curl -4 ifconfig.me` **с выключенным VPN**). Совпадают — белый IP; `100.64–127.x.x` / `10.x` / `172.16–31.x` / `192.168.x` — CGNAT.
2. Белый IP:
   - зарезервировать локальный IP ПК в DHCP роутера;
   - проброс `UDP 7777` → локальный IP ПК;
   - `sudo ufw allow 7777/udp` (если ufw включён);
   - DDNS (DuckDNS / No-IP / встроенный в роутер), т.к. IP скорее всего динамический;
   - сборка **Linux Dedicated Server**, запуск: `./PudgeServer.x86_64 -batchmode -nographics -port 7777` (✅ сборка в batch mode или с `-server` сама стартует сервер и объявляет его в LAN);
   - systemd-сервис для автозапуска и перезапуска.
3. CGNAT — варианты: купить белый IP у провайдера; туннель WireGuard через дешёвый VPS; playit.gg (UDP); Tailscale/ZeroTier (только для друзей). Ngrok и Cloudflare Tunnel не подходят (нет произвольного UDP).
4. **VPN на сервере ломает входящие подключения:** ответы уходят в `tun0` с чужим адресом. Решения:
   - выключить VPN / split tunneling для сервера;
   - или policy routing + привязка сервера к локальному адресу:
     ```bash
     sudo ip route add default via 192.168.0.1 dev wlo1 table 100
     sudo ip rule add from <локальный_IP_ПК> lookup 100
     ```
   - или держать сервер на VPS.
5. Изнутри домашней сети подключаться по локальному IP (NAT loopback на роутере может не работать).
6. Сервер — не от root; все `[Command]` валидировать на сервере (кулдауны, дальность, золото).
7. Перед сборкой игры проверить доступность порта тестовым UDP-эхо-сервером.

## 11. Подготовка эффектов и GPU на старте (2026-11-02)

Запрошен прогрев перед игрой, чтобы уменьшить сильные рывки перед первым эффектом.
Причина на телефоне пока не измерена: возможны создание GPU pipeline state, загрузка ресурсов,
генерация мешей/текстур, выделения памяти и GC. В коде найдена конкретная тяжёлая отложенная работа:
`BloodSplatter.Awake` раньше вычислял атлас 256×256 с волнами, каплями и лучами при первом ударе тела.
Теперь `PrepareTextures` создаёт его и текстуру капли один раз, сохраняет между сценами;
Android вызывает подготовку до доступа к меню. Материалы/меши ManaBurst, AuraRange и материал
Clarity также готовятся заранее. Это не изменяет вид эффектов и не требует пересборки сцен.

`StartupGraphicsWarmup` запускается автоматически только в Android Player с графическим устройством.
В редакторе он запускается явно через `Begin()` (в том числе тестами), не читает и не пишет кэш устройства.
Экран «Подготовка игры…» блокирует указатель и навигацию UI, `OverlayInput` блокирует ввод героя.
Подготовка не меняет timeScale, пресет и игровой счёт, не применяет предметы, не создаёт юнитов
и не проигрывает звуки. Перед работой дожидается первого кадра и применения GraphicsQuality.

Последовательность:

1. Удержать шейдеры `Resources/Effects` и короткие звуки Items/Hook/Trees/Shop загруженными;
   вызвать LoadAudioData до первого применения. Все 286 голосовых реплик повторно не распаковываются.
2. Подготовить ресурсы маны/аур/Clarity и процедурные текстуры крови.
3. На Vulkan загрузить совместимую коллекцию PSO и вызвать `WarmUpProgressively(16)`, ожидая JobHandle
   без блокировки главного потока между порциями. Повреждённый/несовместимый файл игнорируется.
4. На удалённой площадке за пределами игровых камер скрыто отрисовать восемь образцов через
   URP `SingleCameraRequest`: мана, аура, ночной круг, кровь с Color32, капли без Color32,
   LineRenderer для Clarity, выделения и прицела. Есть настоящее освещение и теневой caster;
   skybox DayNightSky отрисовывается этой же камерой. Два состояния тумана (off/linear),
   текущие HDR/MSAA и форматы буферов, включая 32-bit HDR URP. MaterialPropertyBlock применяется
   там же, где его используют эффекты. Глобальные параметры тумана восстанавливаются до yield.
5. При поддержке AsyncGPUReadback дождаться окончания скрытых отрисовок. Удалить временные
   камеру, RT, материалы/меши и экран; оставить только используемые ресурсами кэши и PSO recorder.
6. На Vulkan продолжать запись реальных состояний из меню/арены, сохранять изменившуюся коллекцию
   после подготовки, при уходе приложения в фон и выходе. Во время обычной игры дисковых сохранений нет.

Коллекция: `Application.persistentDataPath/graphics-states-v1.graphicsstate` + `.key`.
Ключ включает buildGUID, Unity version, API, имя GPU, graphicsDeviceVersion (драйвер), ОС.
Пресеты не входят в ключ: коллекция накапливает точные состояния разных пресетов этого же билда.
Это список состояний для прогрева, не переносимый с другого телефона GPU-бинарник;
нативную компиляцию/оптимизацию и собственный pipeline cache выполняют Unity и драйвер устройства.
На GLES скрытая отрисовка работает без GraphicsStateCollection. `WarmupAllShaders` не вызывается:
для Vulkan он не знает всех vertex layouts и render states и может не устранить первый рывок.

Ограничения: скрытый прогон покрывает текущий пресет и известные эффекты, не декартово произведение
всех вариантов URP. Впервые встреченное иное состояние может потребовать компиляции, но попадёт
в коллекцию для следующего запуска. Внешняя смена качества, новые материалы, отличающиеся subpass
и формат экрана могут создать дополнительные PSO. Подготовка удлиняет старт; это не увеличение
постоянного FPS и не гарантия устранения рывков от GC/создания рэгдоллов/тяжёлых самих эффектов.

## 13. Полосы и проценты загрузки (2026-11-02)

Первоначальная реализация; сглаживание и расширенные этапы добавлены в разделе 20.

`LoadingProgress` — общий persistent экран на uGUI: заголовок, отдельная строка каждой
операции с этапом, неинтерактивным Slider и процентом. Прогрев и сцена могут идти одновременно;
Dispose одной операции не закрывает другую. Прогресс ограничен 0–1, не идёт назад, NaN игнорируется.
После завершения 100 % остаются на кадр до закрытия. Указатель блокируется полноэкранным UI,
навигация фокусируется на блокирующей кнопке без действий, `OverlayInput` учитывает экран и
активную загрузку сцены. При смене EventSystem новой сцены фокус захватывается заново;
после последней операции восстанавливается. Фиктивного продвижения по таймеру нет.

`StartupGraphicsWarmup` использует эту же операцию с заголовком «Прогрев шейдеров».
Процент — взвешенная доля выполненной работы, не оставшееся время: загрузка эффектов/звуков,
подготовка ресурсов/атласа, прогрев коллекции (completedWarmupCount/totalGraphicsStateCount),
скрытые отрисовки (DrawCount/фактическое число образцов), ожидание GPU и завершение.
Этап дополнительно показывает счётчик GPU-состояний или отрисовок. Без сохранённой коллекции
её этап пропускается, процент может быстро перескочить вперёд — искусственной задержки нет.
При ошибке прогрева экран убирается через finally и ввод освобождается; 100 % не подделываются.

`SceneLoading`:

- Локальный выход в меню и перезапуск арены используют LoadSceneAsync. Перед стартом операции
  даётся кадр для показа экрана. До активации показывается AsyncOperation.progress (до 90 %),
  затем 95 % «Подготовка сцены» на кадр для её Start и 100 % «Готово» перед снятием экрана.
- Хост: OnServerChangeScene; клиент: OnClientChangeScene. Наблюдатель ждёт создания операции
  Mirror и отслеживает loadingSceneAsync/isLoadingScene. Хост не создаёт второй клиентский
  индикатор. allowSceneActivation, обработка сообщений, ready и спавн остаются у Mirror.
- Пока уже идёт переход, повторные LobbyMessage не запускают новую загрузку меню; отложенный
  reload после остановки сети дожидается предыдущего перехода. Полосы и наблюдатели очищаются
  через Dispose/finally. В режиме без GPU Canvas не создаётся, сетевой lifecycle работает.

Проценты сцен относятся к переходам после запуска приложения. Начальная загрузка движком до создания UI не измеряется; первое меню теперь загружается
из отдельной Boot под экраном прогресса (раздел 14). Unity может выдавать прогресс скачками;
синхронный Awake/генерация ландшафта может на время задержать перерисовку полосы.

Проверено: C# Gameplay, Net, Editor и PlayMode tests компилируются через копии csproj/dotnet
(`-m:1 -nr:false`, Mirror Weaver не запускается), diff и новые GUID проверены. Новые
`LoadingProgressTests` проверяют независимость двух полос, значения/проценты, монотонность,
блокировку ввода и завершение реальной асинхронной загрузки меню. `GraphicsWarmupTests`
дополнены проверкой монотонного прогресса до 100 %; `MenuTests`/`NetworkTests` ждут завершения
экрана при выходе из сети. PlayMode/Android не запускались — Unity открыт. В открытом редакторе
запустить Test Runner → PlayMode → `LoadingProgressTests`, `GraphicsWarmupTests`, `MenuTests`,
`NetworkTests`. Для телефона собрать новый APK; сцены пересобирать не нужно.

Основание: [Unity — AsyncOperation.progress](https://docs.unity.com/en-us/engine/6000.5/script-reference/unityengine/asyncoperation/progress)
и scene lifecycle Mirror 96 в проекте.

## 19. Белёсая пелена на цифрах полос HP и маны (2026-11-03)

становится прозрачным независимо от толщины/масштаба. Дополнительных выборок текстуры,

Полосы, их значения, регенерация, блик, шрифты и прежняя компенсация чёрной обводки сохранены.

Полоса и проценты `LoadingProgress` теперь показывают одно сглаженное значение: целевой
`Progress` остаётся фактической монотонной долей работы, `DisplayedProgress` догоняет его
в Update по unscaledDeltaTime. После длинного кадра шаг времени ограничен, поэтому
следующее обновление не перескакивает сразу к цели. `Complete()` ждёт полной полосы
и оставляет 100 % видимыми на 0.12 с перед закрытием. Независимость операций сохранена.

`SceneLoading` резервирует 0–40 % под ресурсы Unity, 40–45 % под открытие/запуск сцены,
45–97 % под очередь подготовки и остаток под первый кадр/завершение. Локальная загрузка
показывает подпись активации перед allowSceneActivation=true; Mirror только наблюдается,
его allowSceneActivation, ready и сетевой спавн не меняются. Awake/Start могут поставить
работу в очередь через DeferPreparation; перед каждой работой два yield null обеспечивают
отрисованный кадр с названием этапа. Вложенные итераторы выполняются с общим освобождением
ресурсов при ошибке, чтобы экран и блокировка ввода не оставались навсегда.

В MenuLandscape при управляемом переходе генерация вынесена из Awake в очередь:
рельеф, смешивание слоёв земли, применение текстур, деревья, трава и применение её слоёв.
Вычисления проверяют бюджет около 4 мс на небольших порциях строк/попыток, затем отдают
кадр экрану. Синхронный Fill для редакторских сборщиков и прямого входа в сцену использует
тот же алгоритм и локальный RNG; сторона/зерно/состав леса не меняются. Готовая TerrainData
подменяет превью только в конце. В Boot отложенные службы теперь выполняются в этой же
очереди с подписями «Загрузка голоса героя» и «Загрузка сетевых ресурсов»; MainMenu строит
интерфейс после них, отдельным этапом.

Android-прогрев объявляет работу до её начала: шейдеры, звуки предметов/хука/деревьев/
магазина, мана, ауры, Clarity, шрифты, текстуры крови, чтение кэша, GPU-прогрев/отрисовки,
ожидание звуков и сохранение кэша. Генерация атласа крови тоже разбита по кадрам с теми
же формулами и seed. Неиспользованные временные текстуры освобождаются при отмене.
Проценты остаются долей этапов, не прогнозом времени. Нативные вызовы Unity (импорт
ресурсов, применение TerrainData, загрузка шрифтов и компиляция GPU) могут задержать
отдельный кадр: сглаживание не превращает их в фоновую работу.

Проверки: Tools/Check/compile.py собирает игру, Editor и PlayMode-тесты через dotnet
без Mirror-weaver. LoadingProgressTests обновлены под сглаживание и проверяют timeScale=0,
видимость подписей до работы, этапы меню, видимые 100 % и снятие блокировки при ошибке.
LandscapeTests.ProgressiveMenuGenerationKeepsTheSameLandscape сравнивает высоты,
смешивание земли, деревья и траву синхронного и покадрового пути для одинакового seed.
PlayMode и Android не запускались: существует Temp/UnityLockfile, проект открыт.
В редакторе запустить Test Runner → PlayMode → LoadingProgressTests, GraphicsWarmupTests,
LandscapeTests, MenuTests и NetworkTests. Изменения runtime: пересборка Boot/Menu/Arena
не нужна, для телефона требуется новый APK. Пользовательские сцены и ассеты не тронуты.

## 21. Экран до подготовки игровых ресурсов (2026-11-03)

После Unity logo могла оставаться только заливка системной заставки: первая сцена и
runtime callbacks ещё готовились, а экран загрузки сам создавал игровые TMP/SDF-шрифты.
До запуска первого игрового кадра обычный Slider не может показывать работу движка.
Теперь системный splash получает EngineStartup.png: «Подготовка игры», «Запуск движка Unity»
и пустую полосу без процентов. Unity logo сохранён. Blur/затемнение/zoom выключены,
чтобы текст оставался читаемым. Это статичный фон, а не измерение внутренней загрузки Unity.
Он генерируется Tools/Startup/build_splash.py (Pillow + поставляемый LiberationSans),
не подгружает шрифты игры в системную заставку. Ландшафтный Sprite привязан в PlayerSettings;
StartupSplashBuildSettings повторяет настройку через API перед сборкой, если открытый
редактор ещё держит старые PlayerSettings в памяти.

В сохранённой Boot теперь есть один StartupScene без ссылок на игровые ассеты.
Awake создаёт StartupLoadingScreen: непрозрачный Canvas, стандартные Image/Slider/Text
со встроенным LegacyRuntime, плюс минимальную камеру. Первому экрану не нужны TMP,
UiFontLibrary, игровые материалы или InputSystemUIInputModule. После двух yield null
создаётся EventSystem, выполняются отложенные настройки экрана и графики, затем готовятся
шрифты интерфейса. Каждый шаг предварительно получает подпись и кадр для отрисовки;
полоса и проценты сглаживаются по unscaledDeltaTime. Кадр статистики и его ProfilerRecorder
создаются уже под экраном загрузки меню, как голос и сеть.

StartupGraphicsWarmup больше не строит TMP UI в BeforeSceneLoad. Для Boot его автоматический
запуск производится после лёгкого экрана и шрифтов; для прямого запуска Menu/Arena остаётся
AfterSceneLoad на Android. Перед закрытием лёгкого экрана создаётся основной LoadingProgress,
поэтому между ними нет намеренно пустого кадра. OverlayInput учитывает оба экрана.
Обычный интерфейс игры и основной загрузочный экран сохраняют TMP/SDF; встроенный Text
используется только для короткого начального этапа до загрузки игровых шрифтов.

StartupSceneBuilder теперь сохраняет стартовый компонент и настройки заставки.
Boot.unity уже обновлена в репозитории, импортированные ранее Menu/Arena менять не нужно.
Если пересобирать Boot вручную, использовать Pudge Wars → Build Startup Scene.

Проверка: Tools/Check/compile.py — Editor/игра/PlayMode компилируются. Статически проверены
корень и GUID скрипта Boot, GUID Sprite в PlayerSettings, включённый Unity logo, размер PNG,
meta новых ассетов и отсутствие игровых шрифтов в лёгком экране. PNG просмотрен.
LoadingProgressTests.StartupSceneLoadsMenuWithAVisibleProgressBar дополнен проверками,

а после перехода временный экран исчезает. PlayMode/отрисовка Unity/Android не запускались:
Temp/UnityLockfile существует. В открытом редакторе запустить Test Runner → PlayMode →
LoadingProgressTests, GraphicsWarmupTests, MenuTests. Для проверки промежутка после logo
нужна новая сборка на телефоне: редактор не воспроизводит системную заставку при Play.
